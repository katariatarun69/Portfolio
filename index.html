ThailandHotelJobs.com

A hospitality job board and recruitment platform for the Thai hotel industry, built on WordPress and WPJobBoard. Two connected systems: employers post jobs and receive applications, candidates register and are discovered through an anonymized search with a contact request workflow, job alerts, and an AI job description generator.

WordPressPHPWPJobBoardMySQLCustom DB TablesAJAXWP-CronOpenAI APIWeglotWP RocketSMTP

Context

A job board for the Thai hospitality industry, built on WordPress and WPJobBoard across two delivery phases. Employers post jobs and receive applications by email. Candidates register, build a profile, and are found by employers through an anonymized search. The platform is bilingual (Thai and English) and the majority of traffic is mobile.

Foundation

The job board runs on a custom theme with WPJobBoard extended throughout. Employers register through a custom flow with server and client validation, auto-generated usernames, terms agreement tracking, and a token-based email verification step before the account unlocks. Company profiles are set up through a dedicated screen, validated, and auto-activated on first save with a generated slug.

Employer job flow

  • Structured job posting form with dependent Department → Job Title dropdowns and an "Other" free-text fallback
  • Five-job limit per employer session, with an "Add More Jobs" path that flags the account for an offline approval conversation
  • Jobs publish as drafts and go live once approved by an admin
  • Two-week active window per job, with a renewal flow when it lapses
  • Apply-email routing that uses a per-job override address when set, otherwise falls back to the company's primary contact email
  • Featured employer status with a 15-day expiry, tied to the Professional plan and manageable from the user edit screen or a Users list quick action
  • Extra job slot system: admins can grant +1 posting slot for 15 days on top of the plan limit, with a dedicated admin page

Candidate system

  • Registration with PDPA consent validated on both client and server, followed by auto-login and a redirect to the dashboard
  • Profile completion algorithm scored across 11 weighted fields, returning a 0 to 100 completion value used across the dashboard
  • Candidate dashboard with Resume, Applications, Saved Jobs, Job Alerts, Privacy Settings, Change Password, and Account Settings
  • Application list with pagination and single-query job enrichment to avoid N+1 lookups
  • Account deactivation as a soft state, plus permanent deletion that removes the WPJobBoard resume, meta rows, applications, contact requests, and saved-candidate records in one pass

Privacy and contact requests

The core differentiator. A candidate's profile can be Private or Public, and the candidate's chosen setting always takes priority.

  • Private profile: appears in employer search with the current employer hidden, contact details hidden, and previous employers, titles, experience, languages, and desired role visible
  • Public profile: full details visible and the employer can contact the candidate directly
  • Contact request workflow stored in a custom table with a unique constraint on (employer_id, candidate_id), so the database itself enforces one request per pair rather than relying on application checks
  • Statuses: pending, accepted, declined. Declining permanently closes the pair. Accepting reveals contact details on both sides and access survives the candidate switching back to Private
  • AJAX send and respond handlers with nonce and role checks, plus email notifications to both parties on accept and decline

Employer candidate search and saved candidates

  • Anonymized candidate cards showing previous employers, titles, departments, property types, experience, languages, and desired role, with current employer and all personal contact details withheld
  • Filters on location, department, experience, English level, years of experience, and property type, with Department and Job Title as dependent dropdowns against the same master position list used on the posting side
  • Saved candidates stored in a custom table with a unique constraint on (employer_user_id, candidate_user_id), toggled via AJAX and cleaned up on user deletion
  • Saved jobs on the candidate side backed by WPJobBoard's existing shortlist table

Job alerts engine

A custom alerting system on top of the candidate preferences, with three delivery modes: instant, daily, and weekly.

  • Shared query builder used by the alerts list, the sidebar badge count, and the email engine, so matching rules stay in one place
  • Dedup table with a unique key on (user_id, job_id), so a retry or a race condition cannot produce a second email regardless of application logic
  • Cron schedule: a five-minute sweep for instant alerts, a daily digest at 08:00 site time, and a weekly digest scheduled daily but gated to Monday so a missed week self-corrects
  • Unsubscribe links use a hashed token verified with hash_equals, and only stop emails without clearing the candidate's saved preferences
  • Instant alerts skip candidates whose email is unverified or whose account is deactivated

AI job description generator

  • OpenAI integration (GPT-4o-mini) that fills the Job Description and Requirements fields from the posting form in one click
  • Admin settings page under the Job Board menu with editable prompts and eight merge tags: job title, department, location, job type, salary, benefits, other benefits, and company name
  • If the requirements call fails, the description is still returned rather than discarding the work
  • Response is passed through wp_kses_post() before insertion, and the button only renders when an API key is configured
  • Dependent dropdowns and the AI generator shipped together, and both are wired so WPJobBoard's own validation and save path are untouched

Engineering notes

Two pieces of custom engineering are worth calling out.

Deferred mail pipeline. Job applications and candidate registrations were spending 12 to 14 seconds inside synchronous wp_mail() calls, which the user waited through before seeing a redirect. I wrote a must-use plugin that hooks pre_wp_mail on the slow POSTs, queues the payloads, closes the connection with litespeed_finish_request() or fastcgi_finish_request(), and sends the queue in the background. Attachments are copied out of the PHP temp directory first so they survive the request ending. A cron fallback covers hosts without a finish-request function. Measured result: candidate registration went from 13.4s to 0.52s, and job application from around 12s to 0.22s.

Weglot-safe patterns. Because Weglot translates option labels on /th/ pages, the Department → Job Title logic matches on category ID and slug, never on the visible label. The same rule applies to the alert query builder. A prefix helper wraps post_link, page_link, term_link, paginate_links, and the next/prev navigation so links stay language-correct without touching Weglot itself.

The candidate search is locked to logged-in employers only. Job sorting uses a secondary key on ID so same-day jobs never share a position, and timestamps display "Posted today" for same-day items and the actual date for older ones.

Autopotahy Taso

A full redevelopment of a live Czech e-commerce store for custom seat covers. Rebuilt on WordPress 6.x and WooCommerce 8.x, with the existing Configurator, Material Management, Freight/PDF, and B2B/B2C Pricing logic preserved and modernised, then wrapped in a new Bootstrap 5 theme.

WordPress 6.xPHP 8.3WooCommerce 8.xMySQL 8Bootstrap 5WPMLWholesale SuitePDF InvoicesAjax SearchFigma

Problem

The client's existing WooCommerce store ran on an outdated WordPress and PHP stack. Its core value was a custom seat-cover Configurator with Material Management, Freight/PDF generation, and separate B2C and B2B pricing rules. That logic was tightly coupled to the old codebase and couldn't survive a standard upgrade. A rebuild was needed that preserved every piece of custom business logic while modernising the stack and applying a new design.

Solution

Rebuilt the site on WordPress 6.x and WooCommerce 8.x. The Configurator, Material Management, Freight/PDF, and Pricing modules were re-engineered as bespoke plugins compatible with the new core. Existing logic was preserved and modernised rather than rewritten, so no features were lost. A new Bootstrap 5 theme was built from Figma designs, and the legacy catalogue was migrated with script-assisted checksums.

What I built

  • Core plugin redevelopment: Configurator, Material Management, and Freight/PDF modules re-engineered as bespoke plugins compatible with WP 6.x and WooCommerce 8.x, with logic preserved and codebase modernised
  • B2B/B2C pricing engine: role-based dynamic pricing with VAT-inclusive (B2C) and VAT-exclusive plus wholesale discount (B2B) logic, tied into cart and checkout
  • Theme implementation: Figma screens converted to a Bootstrap 5 theme following a 12-column grid and Google Fonts standards
  • Data migration: legacy products, attributes, images, and user roles exported and imported with script-assisted checksums, plus a final import run at cut-over to prevent catalogue drift
  • Third-party integrations: WooCommerce PDF Invoices, WPML for multilingual support, Wholesale Suite, Ajax Search, and approved premium add-ons
  • QA and UAT: cross-browser (Chrome, Firefox, Safari, Edge), responsive, performance, security, and regression testing on the Configurator flow; verified B2C and B2B test orders generate correct PDF invoices

Result

Delivered a modernised WooCommerce store on PHP 8.3, WP 6.x, and WooCommerce 8.x without losing any of the custom Configurator, Material, Freight, or Pricing behaviour the business depends on. B2C and B2B customers both retained their existing pricing and ordering flows, and the site now runs on a supported, maintainable stack. Client sign-off on the UAT checklist completed the project.

Ecommastery 2026

Migration and refresh of a live event-streaming platform, plus a Stripe-driven access pipeline built from scratch. Payments write to Google Sheets through a webhook, a sync cron turns Sheet rows into WordPress users, and a magic-link login system gates two stages of stream access by ticket type.

WordPressPHPStripe APIWebhooksGoogle SheetsApps ScriptWP-CronREST APIBluehost

Problem

The client ran a paid event-streaming site in 2025 with access managed manually through a Google Sheet. For the 2026 edition, the site needed to move to a new domain, get updated visuals and stream URLs, and support two-stage access based on ticket type. The bigger change was payment: last year Stripe was skipped entirely, and this year access had to update automatically after checkout without removing the Sheet from the workflow.

Solution

Migrated the codebase from the old domain to the new one on the same Bluehost account and kept the Google Sheet as the single source of truth for access. Built a three-plugin pipeline: a Stripe webhook receives payment events, verifies signatures, and appends rows to the Sheet; a WP-Cron job reads the Sheet every 15 minutes and creates or updates WordPress users with the correct access flags; a custom user-fields plugin exposes those flags in the admin and generates magic login links with 18-hour expiry.

What I built

  • Stripe webhook plugin: custom REST endpoint at stripe/v1/webhook, manual HMAC-SHA256 signature verification without the Stripe SDK, idempotency check on the buyer email, and a 24-hour transient queue for confirmation emails when the user doesn't exist yet
  • Sheet sync plugin: custom 15-minute WP-Cron schedule that reads the Sheet, looks up users by wp_user_id first and email second, creates new users with unique usernames, backfills the user ID to the Sheet, and propagates email and name changes back to WordPress
  • Access flag logic: elevate_360_access, bdss_access, and access_to_both meta fields, with auto-derivation so a "both" ticket forces both stage flags to Y
  • Magic link login: UUID4 tokens with 18-hour expiry, AJAX generation from the admin profile screen with nonce and capability checks, and token validation handled on template_redirect
  • Admin user fields plugin: adds access flags, three IP allowlist fields, and the generated login URL to every WordPress user profile
  • Two-stage stream gating: Main Stage and BDSS Stage embeds updated with new URLs, visibility driven by ticket type and the April 9 to 11 event dates
  • Code migration: copied all existing code and configuration to the new domain and verified parity with the 2025 site before layering the new payment pipeline on top

Result

Payment to access now runs end to end without manual steps. A buyer pays through Stripe, the webhook appends their row to the Sheet, the sync cron creates the WordPress user with the right access flags, and a magic link email lands in their inbox. The client can still edit the Sheet manually at any time, so the existing workflow stays intact while the automation sits underneath it.

Property Buyers Australia

Two live property platforms for the same client. The first automates property listing, brochure generation, and WhatsApp lead notifications. The second is a paid property-check service with a full request, approval, and refund workflow behind Stripe. Both run on WordPress, both built from custom plugins and a custom theme.

WordPressPHPDompdfGD LibraryACFStripe APIExpedify CRMContact Form 7Webhooks

Context

Two separate sites for the same client. Property Buyers Australia lists properties and captures leads. Property Self Check takes paid property inspection requests and manages them through an approval pipeline. Each site has its own WordPress install, its own custom code, and its own user model.

Site 1: Property Buyers Australia

The client needed a way for non-admin staff to add property listings without touching the WordPress backend. From a single front-end form, a listing should appear on the site complete with a PDF brochure, a branded featured image, and a WhatsApp notification to subscribed contacts.

What I built (Site 1)

  • Custom sub-admin role: a scoped "Property Sub-Admin" role created on plugin activation, with read, create, publish, and delete capabilities limited to listings
  • Front-end submission form: shortcode-driven form on the /add-property/ page, collecting property name, suburb, bedrooms, bathrooms, land size, rental, price, and description, protected by nonce, capability, and sanitisation checks
  • PDF brochure generation: one-page A4 brochure built with Dompdf in a handwritten note style, saved to the Media Library, and pushed to the user as property_<ID>.pdf after submission
  • Branded featured image: PHP GD renders property details onto a pre-designed frame using four bundled fonts (Edu SA Beginner, Playfair Display, Dancing Script, Open Sans), sets it as the post thumbnail, and regenerates it automatically whenever ACF saves a property
  • Status-aware footer: the generated image reads "Property For Sale" or "Property Sold" based on an ACF property_status field, with a lock to prevent repeated regeneration and a manual regenerate action in the admin
  • WhatsApp notifications: a separate notifier plugin hooks publish_property and sends the property slug to an Expedify webhook, which delivers the WhatsApp message with the property link; a _expedify_notified meta flag prevents duplicate sends on edits
  • Lead capture: Contact Form 7 enquiries create contacts in the Expedify CRM with name, email, phone, plus the enquiry subject, message, and originating property title and URL

Site 2: Property Self Check

The client wanted a service where a customer could pay for a property inspection, upload supporting details, and track the request through to delivery. Behind the scenes, an admin team handled documents and a super admin approved or rejected each request, including refunds.

What I built (Site 2)

  • Custom theme: built from scratch on a clean WordPress install, with ACF powering the dynamic homepage content
  • Three-tier role model: User, Admin, and Super Admin, each with its own dashboard, permissions, and visible data
  • User dashboard: property check requests, status tracking (In Review, Pending, Approved, Rejected), star ratings with notes, and a refund request flow
  • Stripe payment: checkout popup for the property check fee, tied to the request creation flow
  • Admin dashboard: request list with counts and status filters, daily, weekly, and monthly views, search, request detail view, and a "send to super admin" action
  • Document handling: multi-file PDF, DOC, and DOCX upload with per-file descriptions, both on the admin and super admin sides, plus file removal
  • Approval workflow: super admin reviews requests, approves or rejects them, and status changes propagate back to the user dashboard
  • Email tab: approved requests only, with an editable template, PDF attachment, and resend capability
  • Refund management: user-side submission with an amount, super admin review with approve or reject actions

Notes

On Site 1, the WhatsApp integration originally called Meta's Cloud API directly. I replaced it with an Expedify webhook because the managed layer handled retries, templating, and duplicate suppression more reliably than the direct API. On Site 2, the refund policy was still being finalised by the client at handoff, so the workflow supports approve or reject without enforcing a specific fee rule.

About

I build from scratch when the project calls for it, and extend what already works when it doesn't. Same instinct either way: don't rebuild what you don't have to.

My work splits roughly evenly between custom platforms built from scratch and production sites that already had users, revenue, or live listings on them. The from-scratch work means designing the data model, the user flows, and the plugin structure. The extension work means understanding what's already there before adding to it, without breaking what's running.

I work close to the client side of things: gathering requirements directly, demoing features as they're built, and taking a bug report through to a fix in production rather than handing it off. Staging before production isn't a formality. It's where I catch the thing that only shows up with real data.

Development approach

On existing sites I start from whatever hooks and data structures are already there before writing anything new. On new builds I design the tables, post types, and roles around what the project actually needs, not around what a plugin ships with by default.

Working style

Direct client communication over long requirement documents. I'd rather confirm a workflow in a five-minute call than guess and rebuild later.

On integrations

Most of what I've shipped has webhooks at the centre of it: Stripe, WhatsApp, OpenAI, Klaviyo, Expedify, Google Sheets. Making the API call is usually the straightforward part. The real work is getting your own backend into the right state before it fires, and handling what comes back reliably.
